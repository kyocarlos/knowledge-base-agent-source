Neo4j Schema 與 Ingest 流程

目標是把不同專案的 Excel 測試報告，轉成可跨報告關聯的圖譜結構，讓使用者能以共通測試項目，例如 Throughput、Latency、Handover 做跨專案搜尋與比對。

Slide 1

問題與目標

現況痛點
  • Excel 報告被切成 chunk 後，只能「找文本」，不容易跨專案關聯。
  • Throughput / Latency / BLER / RTT 常以不同寫法出現，無法穩定對齊。
  • 使用者問「某個測試項目」時，系統容易只找到單份報告或錯誤章節。
  • 如果某份報告沒有對應章節，系統常會誤答其他報告內容。
設計目標
  • 把「報告」與「測試項目」分層，不讓 chunk 直接代表語意主體。
  • 建立 canonical TestItem，例如 Throughput。
  • 讓不同專案報告透過相同 TestItem 節點關聯。
  • 保留原始來源 chunk，方便回溯與引用。
Slide 2

建議 Neo4j Schema

Project

用途：專案維度

例如：SCU2140、SCU2060、SCE2200

{ code, name, owner, domain }
→

Report

用途：報告主節點

Excel 檔案本體

{ doc_name, version, report_type, date, band }
→

TestItem

用途：測試項目標準化

Throughput / Handover / Latency

{ name, canonical_name, aliases[] }

Case / Metric / SourceChunk

用途：數值與證據層

case 編號、數值欄位、原文 chunk

{ case_no, metric_name, metric_value, chunk_hash }

節點與屬性設計

Project
  • code: SCU2140
  • name: 專案顯示名稱
  • domain: 4G/5G / WiFi / Lab
Report
  • doc_name: 檔名
  • report_type: throughput / handover
  • version: V13.8 / V05
  • band: n78 / n79 / n48
TestItem
  • name: Throughput
  • canonical_name: throughput
  • aliases: TCP Throuhgput、UDP Throughput、吞吐量
Section
  • section_no: 4 / 3
  • name: Performance Test / Test Result Summary
  • role: 結構定位
TestCase
  • case_no: 13
  • tdd_slot: DDDSU (4:1)
  • bandwidth: 100
Metric
  • name: DL / UL / RTT / BLER
  • value: 397 / 431 / 28
  • unit: Mbps / ms / %
Slide 4

關係設計

1
Project → Report

(Project)-[:HAS_REPORT]->(Report)

一個專案可有多份報告。

2
Report → Section

(Report)-[:HAS_SECTION]->(Section)

章節做文件內定位。

3
Section → TestItem

(Section)-[:HAS_TEST_ITEM]->(TestItem)

把章節歸到標準測試項目。

4
TestItem → Case

(TestItem)-[:HAS_CASE]->(TestCase)

同一測試項目可跨多 case。

5
Case → Metric

(TestCase)-[:HAS_METRIC]->(Metric)

數值級查詢的核心。

6
Case → SourceChunk

(TestCase)-[:SUPPORTED_BY]->(SourceChunk)

保留原文證據與引用來源。

7
Report → SourceChunk

(Report)-[:HAS_SOURCE_CHUNK]->(SourceChunk)

方便文件級回溯與展示。

8
TestItem ↔ TestItem

(TestItem)-[:RELATED_TO]->(TestItem)

可補上同義/上下位關係。

Slide 5

Ingest 流程：Excel → Graph

流程
  • 1. 讀取 Excel 原始檔與轉出的 md。
  • 2. 偵測報告類型：throughput / handover / simple。
  • 3. 抽出 Project、Report、Section、TestItem、Case、Metric。
  • 4. 產生 canonical TestItem，統一 Throughput / Latency 等名稱。
  • 5. 寫入 Neo4j：先節點、後關係、再 SourceChunk 證據。
  • 6. 同步保留 Qdrant chunk 向量，供語義查詢。
原則
  • chunk 不等於語意主體，chunk 只是證據。
  • 數值型資料要拆成 case / metric，不要只存整段文字。
  • 同一測試項目的命名要先標準化，再建圖。
  • Handover 沒有 Performance Test 時，必須明確標記為無對應章節。
1) ingest_document() ├─ 讀檔 / 轉檔 ├─ 章節解析 ├─ TestItem canonicalization ├─ Case / Metric 抽取 ├─ 寫入 Neo4j 節點與關係 └─ 同步寫入向量庫與 source metadata
Slide 6

查詢流程：使用者問 Throughput 時怎麼找

Graph Path
User Query ↓ Intent: "Throughput" ↓ MATCH (ti:TestItem {canonical_name: 'throughput'}) ←[:HAS_TEST_ITEM]- (Section)-[:HAS_REPORT]->(Report) ↓ 再往下找 TestCase / Metric ↓ 回傳跨專案相關報告與數值
回答策略
  • 若是「列出有哪些報告有 Throughput」→ 直接用 Neo4j。
  • 若是「某個 case 的數值」→ 讀 TestCase / Metric。
  • 若是「哪個報告最相關」→ 結合 Neo4j 與向量庫。
  • 若找不到對應章節 → 明確回覆無對應章節，不亂補值。
Slide 7

實作建議：先做什麼，後做什麼

Phase 1

先建 canonical schema

  • Project / Report / TestItem / Section / TestCase / Metric / SourceChunk
  • 建立唯一鍵與索引
Phase 2

再改 ingest

  • Excel 解析出 structured fields
  • 寫入圖譜前先做 canonical mapping
Phase 3

最後改 query router

  • TestItem 優先查圖譜
  • 數值題只用對應 case / metric
  • 沒有章節就明確說沒有
重點：Neo4j 的價值在於「結構化關聯」，不是單純把 chunk 放進圖庫。要讓 Throughput 能跨專案搜尋，關鍵是 TestItem 標準化 + Case/Metric 結構化 + SourceChunk 證據化。
